## ① Theme Title

**The delegation decision is made by default, not by decision.** Day 5 of Week 8 goes to the practice layer: who delegates, what delegation does to skill, and what the invisible infrastructure (memory, oversight, visibility) does to the outcome. The studies agree on one thing — delegation isn't a property of the task, it's a property of the person and the setup around them: roughly half the variance in assistant use is *who you are*, not *what the task is*; the same smooth AI sessions that feel like success predict smaller skill gains; memory frameworks make pipelines worse until you check for the trap; oversight that can't intervene isn't oversight; and verification that stays invisible lets overreliance spread through a team like a rumor.

## ② Executive Summary

Five papers, one through-line — *the delegation decision is decided before you make it*:

- **Delegation is a default, not a judgment call** (arXiv:2608.19551) — *Delegating or Doing? Understanding User Behavior in Hybrid Human-Agent Interfaces*: N=73 users, 16 realistic scenarios in a hybrid CMS where an MCP-augmented assistant can handle subtasks. **The assistant cut clicks, pages, and scrolling — but did NOT cut task duration.** The surprise: assistant use varied wildly across users on the *same* tasks, and the **ICC = .50** — individual differences account for roughly **half the variance** in who delegates. People carry a delegation style across tasks; the task barely moves it. → Audit Your Prompts.
- **The scaffold that stays on is a substitute** (arXiv:2606.06253) — *When the Scaffold Stays On: AI, Practice Style, and Screening in Elite Skill Formation*: elite competitive programmers (ICPC/IOI, where AI is proctored out) vs. Codeforces (unproctored). An **AI-prompt signature** — more first-attempt acceptances, fewer attempts, fewer debugging retries — predicts **smaller rating gains on unproctored platforms but *higher* non-AI scores at proctored gates**. The same behavior is a complement inside the gate and a substitute outside it; the mode, not the tool, decides what you keep. → **new concept page The Practice Style**.
- **Memory is not free** (arXiv:2608.20202) — *MemTrapBench: Benchmarking Cognitive Traps in LLM Memory Use*: two model families, five memory frameworks, benchmarked against a **no-memory baseline — and every memory framework underperforms the baseline**. Two named traps: **Reasoning Fixation** (the model locks onto its first reasoning path) and **Belief Distortion** (stored memory corrupts fresh reasoning). Pipelines that carry state across runs inherit both. → Build a Tiny Pipeline.
- **Oversight that can't intervene isn't oversight** (arXiv:2603.19213) — *Constitutive vs. Corrective: A Causal Taxonomy of Human Runtime Involvement in AI Systems*: **constitutive** involvement (human work is part of the process — classic human-in-the-loop) vs. **corrective** involvement (human steps in when something goes wrong — human-on-the-loop). Normative Human Oversight, the paper argues, is **corrective + preparedness**: the *capacity* to intervene, with named triggers — not the theater of watching. → First Delegation.
- **Overreliance is contagious** (arXiv:2608.19616, Biswas) — *Modeling AI Overreliance as a Complex Adaptive System*: population-level dynamics of overreliance. Individual verification behavior doesn't stay individual — **reliance propagates through a system**, and overreliance is the emergent equilibrium when verification is invisible. The counter-move: make verification social. → The Reliance Audit + The Daily Standup.

## ③ Concepts Discovered

- **[[02-Key-Concepts/The Practice Style|The Practice Style]]** (new concept, 02 row 40) — the mode you practice in: **substitute** (AI does the reps, skill doesn't build) vs. **complement** (AI accelerates reps, skill grows). Detectable by signature — first-attempt acceptances, fewer attempts, fewer debugging retries — and separated by **proctored gates** (AI-prohibited settings), where the same signature flips from liability to asset. The tool isn't the problem; the mode is.
- **The Delegation Default** — delegation as an individual difference, not a task property (ICC = .50: ~half the variance in assistant use is the person). The audit question changes from "should I delegate this?" to "am I a delegator by default?" — and both defaults are checkable.
- **Memory traps** — two named failure modes for LLM memory: **Reasoning Fixation** (first path wins) and **Belief Distortion** (stored state corrupts new reasoning). The null baseline is the benchmark: if memory doesn't beat no-memory, the memory is the bug.
- **Constitutive vs. corrective involvement** — a causal taxonomy of runtime human roles: being *part of* the process (HITL) vs. *poised over* it (HOTL). Normative oversight = corrective + preparedness: triggers named, intervention possible, drills practiced.
- **Overreliance as population dynamics** — verification is a social behavior with cascade effects; a team where nobody sees anyone checking converges on collective overreliance. Visible verification is an anti-contagion measure, not a performance review.

## ⑤ For the Operator

1. **Name your default.** For one week, note every task where you chose "AI does it" vs. "I do it" — regardless of what the task was. Expect your pattern to hold steady across task types (that's the ICC = .50 finding). Your default is the thing to audit; the task is just the stage.
2. **Schedule proctored reps.** If your AI sessions feel suspiciously smooth — first-try success, no debugging, no retries — that's the substitute signature. Block one no-AI practice session per week on a real task and grade yourself honestly. The gate is what separates practice styles.
3. **Give your pipeline an escape hatch.** If any workflow carries memory or state across runs (drafts, chat history, saved context), add a **no-memory baseline run**: do the same task fresh, from scratch, and compare. If the baseline matches or beats the memory run, the memory is the trap — turn it off.
4. **Pick your loop role before you delegate.** Decide: do I review every step (constitutive), or do I step in on failure (corrective)? If corrective, you need *preparedness* — named trigger conditions and the actual ability to stop the run. Watching without the power to stop is not oversight.
5. **Verify in public once this week.** Do one verification check in a visible channel — a shared doc, a team thread, a post — and say exactly what you checked and how. Reliance is contagious; so is checking.

## ⑥ For the Orchestrator

1. **Design for two defaults, not one average.** With ~half the variance in delegation coming from the person, your team is bimodal: natural delegators and natural doers. Build both lanes — assistant-assisted and fully-automated — and let people opt in/out explicitly. Averages here describe nobody.
2. **Protect skill with proctored gates.** If your team's *capability* is the product (teachers, analysts, clinicians), keep some no-AI moments: unassisted reviews, credential checkpoints, "airplane mode" sessions. The scaffold that stays on is a substitute wearing a productivity costume — the gate is what keeps the mode honest.
3. **Treat pipeline memory as debt.** The evidence is stark: every memory framework in MemTrapBench underperformed the no-memory baseline. Before adding memory to a workflow, document what's stored, why, and how to clear it — and run the quarterly null test (memory off vs. memory on, same task, same rubric).
4. **Write the loop role into every delegation.** Your delegation contracts should name which role the human plays (constitutive or corrective) and what *preparedness* looks like: triggers, stop conditions, intervention drills. Oversight as a checkbox is oversight theater; oversight as capacity is governance.
5. **Make verification visible.** Overreliance is a population-level outcome — it emerges when nobody can see anyone checking. Build a shared verification lane (review log, shared checkpoint, public test results) so that checking is the visible norm. You cannot audit your way out of a contagion; you have to out-signal it.

## Cross-pollination from the AI Agency Knowledgebase

**Automation ≠ augmentation (CentaurBench, arXiv:2608.18554, from the KB's 2026-08-20 digest).** The first benchmark to separate the two regimes — an assistant model either writes help for a weaker worker (augmentation) or produces the deliverable directly (automation) — finds the rankings only modestly correlated: the **automation winner loses augmentation on 5 of 7 tasks**, the **unaided worker outranks every assisted condition on 3 tasks**, and only **one model's guidance beats no guidance on average**. For this wiki's delegation decision: "can it do the task?" (automation) and "does it make *you* better at the task?" (augmentation) are different questions, and the leaderboard answer is the wrong evidence for the delegation answer. The delegation default should be set on assistance-mode evidence — per model, per task, measured against the unaided baseline — exactly as The Practice Style's Weekly Gate measures your own mode.
